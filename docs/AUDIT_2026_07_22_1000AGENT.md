# Full-Contract Audit — 2026-07-22 (multi-agent, per-contract)

**Method.** Per-contract deep audit of all 50 `contracts/src/**.sol` (34k LoC). 125 finder agents
(8 heavyweight contracts split across 3 attack lenses each, mid-size across 2, plus a per-contract
efficiency pass and 7 cross-cutting sweeps), then **every security candidate faced 3 independent
adversarial refuters (majority-refute kills it)**. 266 agent-runs total, ~16.6M tokens. Findings below
were then **hand-verified against file:line** by the maintainer before recording.

**Verdict: 0 Critical, 0 High.** 13 security candidates → 5 survived refutation (1 Medium + 4 Low),
**all fail-closed — no theft, no user-fund loss, no attacker gain.** Consistent with the codebase's 20+
prior hardening passes. Efficiency: 101 validated behavior-preserving gas optimizations.

## Security findings (all fail-closed)

### M-1 (Medium) — Sub-18-decimal swap-fee revenue is permanently unextractable
**`SwapFeeRouter.sol:1600` + `lib/SwapFeeRouterConvertLib.sol:201` + `SwapFeeRouter.sol:175`** · VERIFIED
Swap fees on any token with a Uniswap-V2 WETH pair but <18 decimals (USDC=6, USDT=6, WBTC=8) accrue in
`accumulatedTokenFees[token]` but can never be extracted: (1) `convertTokenFeesToETH` gates on the RAW
balance vs a flat `MIN_TOKEN_FEE_FOR_CONVERSION = 1e18` — for 6-decimal USDC that's ~$1T, unreachable,
and the check precedes the owner multi-hop branch so even the owner can't bypass it; (2)
`withdrawTokenFees` reverts `UseConvertTokenFeesToETH` for any WETH-paired token (AUDIT FIX M4, :1600);
(3) `sweepTokens` reverts identically (:1748). The in-code mitigation note (:167-171) points operators at
`withdrawTokenFees` — the exact path that reverts. **Impact:** permanent loss of the protocol's *own*
revenue (stakers/POL/treasury never receive it); no user funds at risk, no attacker gain. Reachable
permissionlessly, accrues unboundedly.
**Fix (next redeploy):** per-token override for the min-conversion floor denominated in the token's own
decimals (`IERC20Metadata.decimals()`), OR an `onlyOwner`+timelocked token-outbound rescue in
`SwapFeeRouterAdmin` that bypasses the `getPair` guard for provably-blocked balances. Minimal: gate
`withdrawTokenFees` on `accumulatedTokenFees[token] < MIN` (in the token's decimals) rather than on
`getPair` existence.

### L-1 (Low) — `setSequencerFeed` one-shot lacks a mainnet guard (captured-owner brick)
**`SwapFeeRouter.sol:514` (same gap: `TegridyNFTLending.sol:618-629`)** · VERIFIED
The setter only blocks re-setting a *non-zero* feed (:515) and requires the feed be a contract (:521-522),
but has **no `block.chainid == 1` guard**. On mainnet the slot is `address(0)` by design, so a captured
owner can call it once with a malicious feed contract whose `latestRoundData()` returns a down/grace
state → every `convertTokenFeesToETH{,FoT}` reverts via `SequencerCheck`, and (per M-1) withdraw/sweep are
already blocked → swappable-token fees are permanently stranded. No reset path. **Bounded to a captured
key; stranding, not theft.** Sibling `TegridyLending.sol:908` already uses the exact `immutable+chainid`
guard this omits.
**Fix:** `if (block.chainid == 1) revert` in the setter (mainnet never needs a feed), or make the feed
resettable to `address(0)` behind the existing 7-day admin timelock. Fix both SwapFeeRouter + NFTLending.

### L-2 (Low) — Principal window (min/max) lacks the cross-parameter brick-guard
**`TegridyLendingAdmin.sol:383` / `TegridyLending.sol:2539,2166` (NOTE: TegridyLending is NOT deployed)**
`proposeMinPrincipal`/`proposeMaxPrincipal` and their apply-fns never cross-check `min <= max`, unlike the
APR (:2179) and duration (:2187) siblings which all reject a window-inverting value. Since
`MAX_MIN_PRINCIPAL=1e18 > MAX_PRINCIPAL_FLOOR=0.01e18`, a captured admin can set `min=1e18, max=0.01e18`
(both pass individual bounds) → after the 48h timelock `createLoanOffer` (:1015-1016) is unsatisfiable and
all new offers are bricked until a guardian rotates the owner. **Captured-admin brick; no funds at risk.**
**Fix:** mirror the APR/duration pattern — reject `_new > maxPrincipal` in `proposeMinPrincipal` (+ re-check
in apply), reject `_new < minPrincipal` in `proposeMaxPrincipal` (+ re-check in apply).

### L-3 (Low) — FoT conversion TWAP floor computed on gross input strands high-tax-token fees
**`lib/SwapFeeRouterConvertLib.sol:371`**
`convertTokenFeesToETHFoT` sizes its slippage floor from the GROSS `swapAmount` (`twapMin = gross*price*0.985`)
but the actual swap is fee-on-transfer, so `ethReceived ≈ gross*(1-tax)*price*0.997`. For a token with tax
>~1.2% the received ETH is below the floor and it reverts `InsufficientOutput` on every attempt; the one-time
bootstrap escape snapshots a state that forces later conversions through the same gross floor. Combined with
M-1's withdraw/sweep block, the dedicated FoT variant structurally rejects the exact token class it exists to
serve. **Strands only the protocol's own FoT-token fee take.**
**Fix:** size the TWAP floor from the net (post-tax) delivered amount, or route FoT fees through the M-1 rescue path.

### L-4 (Low, KNOWN-DEFERRED) — TegridyTWAP deviation-baseline ratchet
**`TegridyTWAP.sol:914`** · already documented in-source (Spartan audit 2026-07-22) and scheduled for the
TWAP-deepen redeploy. Sole-keeper liveness DoS; fails closed, self-healing, owner-recoverable, oracle currently
dormant. See the NatSpec note at `TegridyTWAP.sol:901-912`.

## Security fixes

### M-1 — decimal-aware conversion floor + a reachable exit

Two halves, because the finding had two independent causes.

1. **`lib/SwapFeeRouterConvertLib.sol`** — the flat `MIN_TOKEN_FEE_FOR_CONVERSION = 1e18`
   raw-unit gate is replaced by `minTokenFeeForConversion(token)`, which returns
   `10 ** decimals()` — *one whole token*, which is what the constant's own NatSpec always
   claimed it meant. At 18 decimals it resolves to exactly `1e18`, so 18-decimal behaviour
   is byte-identical and only the previously-stranded widths change. `decimals()` is read
   by low-level `staticcall`, not `try/catch`: a token returning malformed data makes a
   typed `try` revert *uncatchably* during return-data decoding. Missing / reverting /
   absurd (>36) values fall back to 18 — i.e. the old floor, never anything looser, so the
   SFR-M-02 dust-grief guard stays closed at every width.
2. **`SwapFeeRouter.sol`** — `withdrawTokenFees` / `sweepTokens` gated on pair
   *existence*, which over-shot: `getPair` returns non-zero for any pair anyone ever
   called `createPair` on, including one never funded, and `convertTokenFeesToETH`
   reverts `NoPairForToken` on zero reserves. Such a token had **no** exit at all. The new
   `_hasConvertibleWethPair` requires the pair to exist **and hold non-zero reserves**.
   This does not reopen M3/M4: draining a funded pair to zero requires burning its LP,
   which the owner does not hold for third-party pairs, and a genuinely empty pair is by
   definition one no swap can route through.

The misleading in-code note that directed operators to `withdrawTokenFees` — the exact
path that reverts — is corrected at source.

### L-1 — `if (block.chainid == 1) revert SequencerFeedNotOnMainnet()`

Added to `SwapFeeRouter.setSequencerFeed` and `TegridyNFTLending.setSequencerFeed`.
Ethereum has no sequencer, so mainnet must keep the feed at `address(0)` forever; the
pre-fix setter only refused to overwrite a *non-zero* feed, leaving a captured owner key
one permanent free shot. Mirrors the existing carve-outs at `TegridyLending.sol:840`,
`TegridyNFTLending.sol:556` and `SequencerCheck.sol:163`. The L2 path is untouched.

### L-2 — principal-window cross-guard, both layers

Propose-time (`TegridyLendingAdmin.proposeMinPrincipal` / `proposeMaxPrincipal`) **and**
apply-time (`TegridyLending.applyMinPrincipalChange` / `applyMaxPrincipalChange`), mirroring
the APR (`:2015`) and duration (`:2023`) siblings. Both layers are load-bearing and the
tests prove it independently: the propose-time guard blocks sequential inversion, and only
the apply-time re-check blocks the **parallel-timelock** attack, where both proposals are
queued while the window is still wide and each passes its own propose-time check.

### L-3 — FoT floor sized from the net delivered amount

`convertTokenFeesToETHFoT` sized its floor as `gross * price * 0.985` while the swap
delivers `gross * (1 - tax)`, so any tax above ~1.2% made the floor structurally
unreachable — the dedicated fee-on-transfer variant rejected exactly the token class it
exists to serve. The floor now splits in two: the caller's `minETHOut` and the absolute
multi-hop anti-drain floor are **never rescaled**, while the price-derived component is
rescaled by the ratio the first-hop pair *actually* received, measured from that pair's own
`balanceOf` delta rather than anything the token self-reports. `MAX_FOT_TAX_BPS = 3000`
bounds how far a hostile token can shrink its own floor by under-delivering; beyond that
the conversion reverts `FoTHaircutTooLarge` instead of executing against a vestigial floor.
Moving the price gate after the swap concedes nothing — the transaction unwinds atomically,
so sandwich protection is unchanged (pinned by `test_L3_rescaledFloor_stillBlocksSandwich`).

### L-4 — TWAP deviation baseline seeded from the interval TWAP

`lastSpot{0,1}` is written from the cumulative-derived interval average instead of the raw
instantaneous reserve ratio. Moving the anchor now costs holding the price for a whole
interval rather than for one block. Branch conditions are untouched — only the **value**
written differs. Uniswap V2's own oracle ignores intra-block price for the same reason.

### Money-conservation harness (residual gap #2, now closed)

`Audit_1000Agent_FeeConservation.t.sol`. Conservation **alone would not have caught M-1** —
a stranded balance still balances. The invariant that catches it is **reachability**:

- **INV-1 (no stranding)** every token holding a *material* balance has at least one exit
  that is not structurally blocked, probed by attempting each exit and rolling state back
- **INV-2** token balance >= `accumulatedTokenFees`
- **INV-3** ETH balance >= `accumulatedETHFees + totalPendingDistribution`
- **INV-4** accrued == still-accounted + converted-to-ETH + delivered-to-treasury

"Material" is defined as one whole token computed *by the test* from `decimals()`, never
read from the contract under test — a bug that inflates the contract's own floor (exactly
M-1) would otherwise also inflate the threshold and the invariant would skip the very
balances it exists to police. Sub-one-token dust is deliberately out of scope: it is
pre-threshold, not stranded, and exits as soon as accrual crosses one whole token.

## Two CI facts worth acting on separately

1. **`test/invariants/` runs in no pipeline.** The Contracts CI matrix matches
   `test/<Prefix>*.t.sol` globs that never descend into that directory, and the "nightly
   cron" its comments defer invariant runs to **does not exist** — the only scheduled
   workflow in `.github/workflows` is CodeQL. Twelve invariant suites are currently dead
   weight. The new harness is at `test/` root for this reason.
2. **`block.timestamp` is unsafe in tests under `via_ir = true`.** The IR optimiser
   common-subexpression-eliminates the TIMESTAMP opcode across external calls — sound
   on-chain, but `vm.warp`/`skip` violate it. Deadlines written the obvious way evaluated
   against the *pre-warp* timestamp and reverted `DEADLINE_EXPIRED`, which silently
   satisfied bare `vm.expectRevert()` assertions — tests passing for the wrong reason. The
   new suites read time through `vm.getBlockTimestamp()` and assert on specific selectors.
