1. *"fix up the staking module it looks so elementry — fix the days to lock to
   should be buttons 7 days month 3 months year and such with shows how much

## 1. The staking module (`LighthousePoolLive.tsx`)

Rebuilt against the venue's own TOWELI `StakingCard`, which is the reference
the operator named.

**Lock duration is a radiogroup of buttons**, not a number spinner: `1 Day ·
7 Days · 30 Days · 90 Days · 6 Months · 1 Year`, generated by
`lockPresets(pool)` from the venue's `LOCK_OPTIONS` idiom and **clamped to what
the program will accept** — a preset outside `[minDuration, maxDuration]` is
dropped, and the pool's own bounds are always the first and last button even
when they are not round numbers. `role="radiogroup"` + `aria-checked` + a
checkmark, same accessibility shape as the TOWELI card (the selection is never
conveyed by background colour alone). A free-form `or exactly __ days` field
stays, because every duration in the window is legal and the presets are a
convenience, not the range.

**Each button carries the rate that lock earns** — the operator's "shows how
much yield in percent even if 0". On this pool all six read `109.5%`, and the
line under them says why: the weight is flat.

**The rate is shown twice and the two are never conflated.** Four stat tiles
head the card:

- `Reward vault` — straight off-chain, 0 renders as a labeled real zero;
- `Total staked`;
- `Paying now` — **0% APR**, because a configured rate that no vault can back
  pays nothing;
- `Configured` — **109.5% APR**, labeled as configuration.

Under them, in amber: *"Paying now is 0% because the reward vault is empty. The
pool is configured to pay 109.5% a year, but a rate only pays out of a funded
vault."* This is the shape the funding-last contract and
`STAKING_LOOK_2026_08_24.md` §2.2 demand — the rate is never printed alone.

**Also new, all of it read rather than assumed:**

- amount field with a real wallet balance and a MAX fill, and an
  over-balance refusal before the wallet ever sees the transaction;
- projected rewards at 30d / 90d / 1y — which read **0** while the vault is
  empty, with the configured-rate figure stated beside them rather than
  substituted for them;
- your positions now show weight, accrued rewards (via the SDK's own
  `calcRewards`, over the real on-chain reward entry), and the unlock date;
- **Unstake is disabled until the lock opens**, with the countdown on the
  button. It was always enabled before, so the only way to learn that the
  program refuses (`"Stake is locked, unstake is not possible"`) was to sign a
  transaction and watch it fail;
- vault runway ("this vault funds about 12d at today's stake and rate") —
  renders only when there is both a funded vault and a stake, and refuses to
  answer otherwise;
- the reward vault address is linked, with its `permissionless` flag stated.

**Mint decimals are now read on-chain** (`getParsedAccountInfo`) instead of the
hardcoded `DECIMALS = 6`. Decimals scale every human number *and* the reward
rate itself, which is quoted per raw unit — a wrong constant would misprice the
whole card.

### The math seam

`bungalowStaking.ts` gained display math so the UI can answer "what does a
30-day lock earn?" synchronously. The house rule is battle-tested code only, so
these are **exact transcriptions of the SDK's own** `calculateStakeWeight` and
`calculateRewardRateFromAmount`, and `bungalowStakingRates.test.ts` pins them
against the real SDK functions (not a mock) over a grid of durations, weights
and decimal pairs. They compute nothing that rides a transaction — every amount
and duration the wallet signs still comes from the SDK's prepare paths.

## 2. The Solana swap, wired (and a chain switch)

**The bug was a conflated gate.** `isSolanaConfigured()` answered
*"does the venue have a fee account?"* (`VITE_SOLANA_FEE_ACCOUNT`) and was used
to gate *"does the Solana swap exist?"*. With no fee recipient set:

- `/solana` rendered `FeatureNotDeployed`;
- the nav hid it (`SOLANA_LIVE`);
- `bungalowTradeRoute()` sent every Solana bungalow **out to jup.ag**;
- and `PRIMARY_NAV`'s "Trade" pointed at `/swap`, the Ethereum surface.

So the venue's own Solana token had no in-venue trade route, and "Trade" in the
BAYLA bungalow meant an Ethereum swap that cannot touch her. The missing piece
was a fee *recipient* — a reason to charge nothing, not a reason to send
traffic away. `jupiter.ts`'s `feeEnabled()` already kept `platformFeeBps` and
`feeAccount` coupled (sending neither when unset), so the swap itself always
worked.

Split into two honest gates in `lib/solana.ts`:

- `isSolanaFeeConfigured()` — the old body. Drives the fee line only.
- `isSolanaSwapLive()` — the surface. The Jupiter proxy (`/api/jupiter` →
  `api/aggregator.js`) and the RPC proxy (`/api/solrpc`) are same-origin and
  deployed regardless, so: live.

The fee disclosure now tells the truth either way — *"No platform fee is
charged here today — you get Jupiter's route as quoted"* when unset, the
`{feePct}%` line when set. Setting `VITE_SOLANA_FEE_ACCOUNT` later flips it with
no code change.

**`ChainSwitch`** (`components/swap/ChainSwitch.tsx`) is mounted at the top of
**both** surfaces: `Ethereum · TOWELI · Uniswap / CoW` | `Solana · BAYLA ·
Jupiter`. Plain links, because the two surfaces are separate routes with
separate wallets — the URL is the state. `?out=<mint>` survives the round trip,
and the Solana half names the active bungalow's token when there is one.

**`TRADE_ROUTE`** in `navConfig.ts` now resolves "Trade" to `/solana` when the
active bungalow is a Solana one. Resolved at module scope like every other gate
in that file (a bungalow switch persists + reloads). It is a default, never a
trap: `ChainSwitch` keeps the other surface one click away, and
`navConfig.test.ts` pins both directions.

## 3. The Bayla dashboard

The old page was one column of full-width cards with the position — the thing a
dashboard is *for* — missing entirely.

**It was also lying.** The connect card still read *"there is no pool to
deposit into yet, so nothing here will ever ask"*, written before the pool
existed and still on the page two days after the mainnet ceremony. Same
stale-claim class the farm hero was fixed for on 2026-08-27; the copy now
branches on the same registry fact (`stakePool`) the farm panel does.

Now a three-card "your standing" row above the market:

1. **Wallet** — balance, USD (only when the price endpoint actually answered),
   connect/disconnect.
2. **At the lighthouse** — staked, accrued, open positions, next unlock, with
   the empty-vault caveat and a link to manage. Three honest states: not
   connected → "the pool is live"; connected with nothing staked → "nothing
   staked yet" + a stake CTA; staked → the numbers. Self-hides for a bungalow
   with no pool, and never fetches the SDK chunk for one.
3. **Live surfaces** — trade / pool / scan / the real liquidity pairs, plus the
   contract address with a copy button (which this page never showed).

Then the market strip + chart, holders, and heat, unchanged.

## 4. Two findings for the operator

### 4.1 The pool grants no duration bonus — `maxWeight == minWeight == 1.00x`

Locking for a year earns exactly what locking for a day earns. Only the exit
date changes. This is a property of the pool as created on 2026-08-26, not a UI
choice, and the panel now says it out loud rather than implying a boost curve
that does not exist.

If the intent was TOWELI-style *"lock longer, earn more"*, that needs a **new
stake pool** created with `maxWeight > SCALE_FACTOR_BASE` (e.g. `2e9` for 2x at
365 days) — `maxWeight` is set at pool creation. Everything else is already
built for it: `stakeWeightScaled` implements the program's real curve, the lock
buttons would immediately show different rates per lock, the positions list
would show each entry's multiplier, and the "this pool weights every lock the
same" line would swap itself for the boost copy. Nothing in the UI needs
touching. A second pool means migrating stakers, so this is a deliberate call,
not a fix.

### 4.2 The reward pool is permissionless — anyone can fund it

`permissionless: true`. The vault address is now linked on the panel with that
stated, which is as far as this change goes. A one-click **"Top up the reward
vault"** button is a small addition — the SDK ships `fundPool` — but it was
deliberately left out: `prepareFundPoolInstructions` creates a Streamflow
treasury ATA when `streamflowFee > 0`, i.e. the protocol takes a cut of a
funding transfer, and shipping a money-path button without first reading and
disclosing that number is the kind of quiet substitution this repo's honesty
rules exist to stop. **Ask for it and it gets built with the fee read on-chain
and printed.**

### 4.3 The vault is still empty

Unchanged and unchangeable from here — §4 of `BAYLA_BUNGALOW.md` still holds.
Until someone funds `G4WFqZcq…uUcV`, "paying now" is 0% and the panel says so
in four places.

## 5. Supersedes

`BAYLA_BUNGALOW.md` §5 first bullet — *"No APR, no runway … anywhere in the
UI"* — was written 2026-08-24, when the pool did not exist and any rate would
have been invented. The pool now exists and publishes its own rate on-chain, so
the rule it was protecting is served differently: the **configured** rate is
shown and labeled as configuration, the **paying** rate is shown as the real 0
it is, and runway renders only when a funded vault and a live stake both exist.
No number on the surface is synthesized; every one of them is read.
