# Slither `dead-code` detector — re-enabled 2026-05-03

## Date
2026-05-03

## Reason for re-enable
Fresh-eyes audit found that excluding the `dead-code` detector was hiding
genuinely-unreachable functions (B7-class findings — unreachable
internal helpers, abandoned legacy entry points, and orphaned modifiers
left behind after refactors). The previous rationale ("Many helpers
retained for ABI compatibility and future use") was applied too
broadly: ABI-compatibility helpers are **public/external** and Slither
correctly does not flag those as dead. The detector only fires on
`internal`/`private` functions with no callers, which is exactly what we
want surfaced in a live audit.

## How to suppress per-line if a finding is intentional
Use the inline pragma directly above the function (or contract member)
that should be exempted:

```solidity
// slither-disable-next-line dead-code
function _abiKeptForFutureMigration(address user) internal view returns (uint256) {
    // Documented future-use helper — referenced from off-chain ABI codegen
    // tooling but not yet wired up in any on-chain call path. See B7-batch
    // ledger entry 2026-05-03 for justification.
    return _shadowState[user];
}
```

## When NOT to suppress
- The function is genuinely unreachable: **delete it**, do not suppress.
- The function is reachable only via `delegatecall` from a known proxy:
  add a `// slither-disable-next-line dead-code` AND a one-line comment
  pointing at the proxy.
- The function is reachable but Slither cannot infer the call (e.g.
  invocation built from `abi.encodeWithSelector` in another contract):
  prefer adding a unit test that hits the path; the test itself becomes
  the call site Slither can see.

## How to verify locally
```
cd contracts
slither . --config-file ../slither.config.json --detect dead-code
```
