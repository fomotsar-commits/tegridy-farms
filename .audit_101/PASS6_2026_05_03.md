## 2. The five contract HIGHs

### 2.1 LD-NEW-H1 — cross-loan reward theft via stale `loanId`

**Surface:** `TegridyLending.pullEscrowRewards(uint256 loanId)`
**Closed:** [`TegridyLending.sol:1620-1633`](../contracts/src/TegridyLending.sol#L1620) (commit `722d1f1`)

**Pre-fix:** the function blindly invoked `staking.claimUnsettledForTokenId(loan.tokenId, recipient)` for the recipient stored on the *historical* `loanId`. The credits in `unsettledRewardsByTokenId[tokenId]` belong to whichever loan currently has the NFT escrowed — but a stale-loan recipient could call this on their own old `loanId` while a NEW loan was active on the same tokenId, and silently drain the new borrower's accruing kick rewards.

**Fix:** before invoking the per-tokenId pull, the function checks `staking.ownerOf(loan.tokenId) == address(this)` — if the NFT is currently held by *this* lending contract, the per-tokenId credits belong to the active loan and must be paid out via that loan's settlement scope (repay / claimDefault), not via a stale-loan side-pull. The legacy `escrowRewardsOwed[loanId]` path is preserved for any pre-fix entries.

**Cross-protocol mirror:** the same shared-mapping shape exists in `TegridyRestaking.claimResidualForTokenId`. A prior restaker still set as `residualClaimant[tokenId]` could drain the per-tokenId mapping while the NFT was escrowed in lending. Closed in commit `8266289` at [`TegridyRestaking.sol:1163-1195`](../contracts/src/TegridyRestaking.sol#L1163) — the function returns 0 paid and emits `ResidualPullDeferredCrossHolder` when `staking.ownerOf(tokenId)` is neither this contract nor `msg.sender`. Residual claim stays live for retry once the NFT exits lending.

**Regression tests:**

```
test_LD_NEW_H1_oldLoanCannotDrainNewLoanCredits
test_LD_NEW_H1_mirror_residualClaimantBlockedByLendingEscrow
```

### 2.2 LD-NEW-H2 — silent no-op `transferFrom` on outbound NFT leg

**Surface:** `TegridyNFTLending.repayLoan` and `claimDefault` (outbound NFT transfer)
**Closed:** [`TegridyNFTLending.sol:620-697`](../contracts/src/TegridyNFTLending.sol#L620), [`L755-771`](../contracts/src/TegridyNFTLending.sol#L755) (commit `722d1f1`)

**Pre-fix:** ERC-721 `transferFrom` returns `void`. A whitelisted (but later-discovered-malicious) collection could override `transferFrom` to *silently no-op* — return successfully without moving the token. The lending contract would mark `loan.repaid = true`, send ETH to the lender, and never set `stuckCollateralRecipient`. The NFT would stay locked in lending forever.

**Fix:** new `_safeOutboundTransfer` helper performs the `transferFrom` then re-checks `ownerOf(tokenId)` post-condition. When the post-transfer owner is not the intended recipient, the helper emits `CollateralRedirected(tokenId, collection, intendedTo, actualOwner)` and the caller sets `stuckCollateralRecipient[loanId] = recipient` so the borrower (or lender on default) can recover via `claimStuckCollateral` once the collection is replaced or fixed.

**Regression test:** `test_LD_NEW_H2_silentNoOpRepay_marksStuck` — a `P6_NoOpERC721` (silent-no-op `transferFrom` override) demonstrates: loan settles (money flows), NFT stays in lending, `stuckCollateralRecipient[loanId]` is now the borrower (was 0 pre-fix), and the borrower recovers via `claimStuckCollateral` once the collection is unfrozen.

### 2.3 TWAP HIGH-2 — `consult()` ignored `factory.disabledPairs`

**Surface:** `TegridyTWAP.consult(pair, …)`
**Closed:** [`TegridyTWAP.sol:472`](../contracts/src/TegridyTWAP.sol#L472) (commit `722d1f1`)

**Pre-fix:** the FRESH-EYES H-2 fix added a `disabledPairs[pair]` check on `update()` — but the *read* side (`consult()`) had no such gate. A pair disabled mid-window left the buffer's most recent observations recorded against frozen-skewed reserves; consult would happily integrate over them and serve a poisoned price to lending oracle, POL harvest, and TegridyLending's ETH-floor read.

**Fix:** consult now reverts `PairDisabled` when `factory.disabledPairs(pair)` is true. Forces consumers to fall back to their fail-closed paths until governance re-enables and an honest post-resume observation anchors the next consult.

**Regression test:** `test_TWAP_HIGH_2_consultRevertsWhenPairDisabled` — seeds 4 honest observations, asserts `consult()` works, flips `disabledPairs[pair] = true`, asserts both `consult()` and `update()` revert `PairDisabled`, then re-enables and asserts consult resumes.

### 2.4 TWAP HIGH-3 — first observation skipped deviation gate

**Surface:** `TegridyTWAP.update(pair)` — first call for a new pair
**Closed:** [`TegridyTWAP.sol:309-331`](../contracts/src/TegridyTWAP.sol#L309) (commit `722d1f1`)

**Pre-fix:** the deviation gate compared the new spot price to `lastSpot{0,1}` from the prior observation — but the *very first* observation on a new pair had no prior to compare against. An attacker creating a pool at a manipulated 1:100 ratio (asymmetric initial liquidity), then calling `update()`, anchored a poisoned baseline. Subsequent observations within ±50% of the manipulated anchor passed the deviation gate and downstream consumers silently read the lie.

**Fix:** when `observationCount[pair] == 0`, the first observation is now stamped `bypassed = true` and `lastBypassUsed[pair] = block.timestamp`. The bypass marker reuses the existing `best.bypassed` consult guard (D-AMM-M5 / V2-AMM-H1 lineage). Tests realigned to ≥3-observation seeding so the bootstrap rolls out of the lookup window before any consumer trusts it.

### 2.5 SwapFeeRouter HIGH-4 — multi-hop snapshot drift

**Surface:** `convertTokenFeesToETH` and the FoT variant — multi-hop branches
**Closed:** [`SwapFeeRouter.sol:1554-1563`](../contracts/src/SwapFeeRouter.sol#L1554) and [`L1652-1660`](../contracts/src/SwapFeeRouter.sol#L1652) (commit `722d1f1`)

**Pre-fix:** repeated owner multi-hop conversions bumped `lastConvertedAt[token]` (cooldown) but left `lastConversionSnapshot[token]` frozen (the snapshot logic was 2-hop-only because multi-hop has no direct-pair anchor). Days/weeks later, the next permissionless 2-hop call computed `elapsed = currentTs - prev.timestamp` over the entire intervening period — the time-averaged TWAP between the stale anchor and now diverged sharply from current spot, producing a `twapMin` floor that admitted sandwich at near-current spot.

**Fix:** the multi-hop branches now invalidate any prior snapshot (`timestamp = 0, cumulative = 0`). The next 2-hop call sees no anchor and falls through to the bootstrap (owner-only) branch, where the operator must supply an explicit off-chain `minETHOut` policy. Mirror code lives in both `convertTokenFeesToETH` and its FoT variant so they stay in lockstep.

## 3. The five contract MEDs

### 3.1 PASS5-PA-L1 (re-classified MEDIUM) — extension double-counted `consumedEscrow`

**Surface:** `PremiumAccess.subscribe` extension branch
**Closed:** [`PremiumAccess.sol:309-330`](../contracts/src/PremiumAccess.sol#L309) (commit `722d1f1`)

Pass-5 found this as LOW. Promoted to MEDIUM after pass-6 traced the impact: governance proposals citing `totalRevenue` were over-reporting by `2× consumedEscrow` per extension cycle, which is non-negligible when subscriptions extend frequently. The funds-at-risk axis is still LOW (refund cap remains satisfied), but the metric integrity matters for governance signal. Fix: drop the `totalRevenue += consumedEscrow;` line at the prior line 317. Test harness aligned to the corrected exact-2x trajectory in [`contracts/test/PremiumAccess.t.sol`](../contracts/test/PremiumAccess.t.sol).

### 3.2 N-1 GaugeController orphan

**Surface:** `proposeRemoveGauge` / `executeRemoveGaugeNextEpoch`
**Closed:** [`GaugeController.sol:201,788`](../contracts/src/GaugeController.sol#L201) (commit `722d1f1`)

Pre-fix, calling `proposeRemoveGauge` while a prior `executeRemoveGaugeNextEpoch` had left `pendingGaugeRemove` non-zero silently overwrote the staged gauge. The original was orphaned in `gaugeList` with `isGauge=false`, slowly filling the list to `MAX_TOTAL_GAUGES = 50` and bricking `proposeAddGauge`.

Fix: new `error GaugeRemovePending()` (line 201). `proposeRemoveGauge` now reverts with this error when `pendingGaugeRemove != address(0)` (line 788), forcing the operator to call `cancelRemoveGauge` or wait for the in-flight remove to land before staging the next.

### 3.3 F-1 Restaking under-credit on historical lookups

**Surface:** `TegridyRestaking._boostedAmountAt(_user, _timestamp)`
**Closed:** [`TegridyRestaking.sol:486-512`](../contracts/src/TegridyRestaking.sol#L486) (commit `722d1f1`)

Pre-fix, when `block.timestamp >= liveLockEnd` the function returned `min(cached, current)`. Once an attacker (or honest decay sweeper) called `staking.kick()` to zero `current` after lockEnd, every historical RevenueDistributor.claim against an epoch that snapshotted the user during their active lock returned `min(cached, 0) = 0` — wiping out the user's legitimate share for prior epochs. Direction-of-error is opposite the original DR-04 over-credit but equally a wrong answer.

Fix: split the predicate. For `_timestamp < liveLockEnd` (the user *was* active at that historical instant), return `cached` directly. For `_timestamp >= liveLockEnd` (lock has decayed), keep the `min(cached, current)` clamp. Preserves the DR-04 / DR2-02 over-credit defense while restoring honest historical accounting.

### 3.4 F-2 Restaking attribute-cap

**Surface:** `executeAttributeStuckRewards` (and the matching `proposeAttributeStuckRewards` cap)
**Closed:** [`TegridyRestaking.sol:1389-1408`](../contracts/src/TegridyRestaking.sol#L1389) (and the symmetric cap at [L1334](../contracts/src/TegridyRestaking.sol#L1334)) (commit `722d1f1`)

Pre-fix, the unattributed-pool calculation only subtracted `totalUnforwardedBase`. A captured-or-colluding owner could `proposeAttributeStuckRewards` for an amount that included `totalActivePrincipal` and `totalPendingUnsettled` — i.e., credit a chosen restaker with rewards that were actually backing OTHER users' principal reservations.

Fix: subtract both `totalActivePrincipal` and `totalPendingUnsettled` from the unattributed pool; the attribution path is now bounded by the actually-unattributed bucket, not the gross balance.

### 3.5 LD-NEW-M4 — TWAP staleness clock-skew underflow

**Surface:** `TegridyLending` — TWAP staleness gates
**Closed:** [`TegridyLending.sol:1245`](../contracts/src/TegridyLending.sol#L1245), [`L1256`](../contracts/src/TegridyLending.sol#L1256) (commit `722d1f1`)

Pre-fix, the staleness check was `block.timestamp - latest.timestamp > TWAP_MAX_STALENESS`. A bridged feed or sequencer replay producing `latest.timestamp > block.timestamp` (the V3-LIB-M1 fix already hardened SequencerCheck against this same shape) would underflow Solidity 0.8 checked-math `Panic(0x11)`, bricking every lending operation reading the floor.

Fix: directional pre-check `if (latest.timestamp > block.timestamp) revert OracleStale();` ahead of the subtraction. Same shape applied to the dormancy-bypass cooldown using `lastBypass`.

### 3.6 MEDIUM-5 — POL harvest deviation gate too wide

**Surface:** `POLAccumulator.HARVEST_TWAP_DEVIATION_BPS`
**Closed:** [`POLAccumulator.sol:131`](../contracts/src/POLAccumulator.sol#L131) (commit `722d1f1`)

Pre-fix, the deviation gate allowed 200 bps drift between spot and TWAP at the moment of `executeHarvestLP`, but the per-leg `TWAP_SAFETY_BPS` was only 50 bps. An attacker pushing spot 1.99% off TWAP passed the gate and extracted ~1.5% per harvest (the 0.5% per-leg margin couldn't backstop the full 2% drift).

Fix: narrow `HARVEST_TWAP_DEVIATION_BPS` from 200 → 50. The two thresholds now align — deviation gate requires reserves within the same tolerance as the per-leg slippage floor.

## 4. Frontend CRIT / HIGHs / LOW

### 4.1 FE-HIGH-01 — TegridyDropV2 `mint()` ABI mismatch

**Surface:** [`frontend/src/lib/contracts.ts:420-421`](../frontend/src/lib/contracts.ts#L420), [`frontend/src/hooks/useNFTDropV2.ts`](../frontend/src/hooks/useNFTDropV2.ts)
**Closed:** commit `b1fb6d4`

Frontend ABI declared `mint(uint256, bytes32[])` (2 args). The actual Solidity signature is `mint(uint256 quantity, uint256 allowedAmount, bytes32[] proof)` (3 args). Selectors differed — every Drop V2 mint UI call reverted at the dispatcher. The 2-arg selector could also collide with a future contract function. Fix: extend the ABI to 3 args; `useNFTDropV2.mint()` accepts an optional `allowedAmount` (default 0 keeps PUBLIC-mint callers compatible; ALLOWLIST callers must pass the merkle-leaf-encoded per-wallet cap).

### 4.2 FE-HIGH-02 — SIWE client missing `expirationTime` + `notBefore`

**Surface:** [`frontend/src/nakamigos/lib/siweAuth.js:41-60`](../frontend/src/nakamigos/lib/siweAuth.js#L41)
**Closed:** commit `b1fb6d4`

Server's `verifySignature` (`/api/auth/siwe`) requires `expirationTime` and `notBefore` on the SIWE payload — pre-fix the server rejected every legitimate login from this client with HTTP 400 ("expirationTime required"). Fix: `buildSiweMessage` now sets a 5-minute `expirationTime` window aligned to server's `MAX_MESSAGE_TTL_MS` plus a 30s `notBefore` clock-skew tolerance.

### 4.3 FE-LOW-04 — `useWaitForTransactionReceipt` missing `chainId`

**Surface:** [`frontend/src/hooks/useLPFarming.ts:24`](../frontend/src/hooks/useLPFarming.ts#L24), [`frontend/src/hooks/useNFTDropV2.ts:43`](../frontend/src/hooks/useNFTDropV2.ts#L43)
**Closed:** commit `b1fb6d4`

Without `chainId`, viem's underlying call listened on the wallet's CURRENT chain. If the user switched chains mid-flight (or clicked "switch network" right after submitting), confirmation listened on the wrong chain and silently never fired. Fix: pin `chainId: CHAIN_ID` on both hooks' `useWaitForTransactionReceipt` calls.

### 4.4 FE-CRIT-01 — open-proxy aggregator rewrites in `vercel.json`

**Surface:** seven `vercel.json` rewrites to upstream DEX-aggregator hosts
**Closed:** commit `975e5af`

Pre-fix, `vercel.json` had `/api/{odos,cow,lifi,kyber,openocean,paraswap,swapapi}/:path*` rewrites that proxied directly to upstream APIs with no gating. Anyone could `curl https://tegridyfarms.xyz/api/odos/<arbitrary>` to (a) burn upstream quota associated with our origin/IP, (b) send arbitrary POST bodies through our trusted host, (c) have the upstream response served back through our trusted origin (cookie scope, referer, edge-cached for other users).

**Fix:** each rewrite is replaced by a Vercel serverless function under `frontend/api/{provider}/[...path].js` that enforces seven gates via shared infra in `frontend/api/_lib/aggregator-proxy.js`:

1. **Method allowlist** — only GET or POST per provider; everything else 405.
2. **Origin allowlist** — fail-closed in production (tegridyfarms.xyz / vercel.app / nakamigos.gallery / `ALLOWED_ORIGIN`); permissive in dev; `*.vercel.app` honored when `VERCEL_ENV === preview`.
3. **Rate limit** — Upstash sliding window (60/min/IP); fail-closed in prod when Upstash env missing.
4. **Path allowlist** — exact-prefix match per provider with decode-then-check so `%2F..%2F` traversal cannot be smuggled.
5. **Body cap** — 32 KB request cap; `readBoundedText` 5 MB response cap (gzip-bomb defense).
6. **Query allowlist** — explicit per-provider whitelist; `apiKey` / `cookie` / `authorization` are NOT forwarded.
7. **Response cleanup** — `Set-Cookie` and `Authorization` are NOT echoed back; `Cache-Control: private, no-store` by default; upstream non-2xx collapsed to opaque 502.

Per-provider endpoint allowlist (matches actual usage in `frontend/src/lib/aggregator.ts`):

```
odos       POST /sor/quote/v2
cow        POST /mainnet/api/v1/quote
lifi       GET  /v1/quote
kyber      GET  /ethereum/api/v1/routes  (X-Client-Id set server-side)
openocean  GET  /v4/eth/quote
paraswap   GET  /prices
swapapi    GET  /v1/swap/{chainId}       (chainId allowlist: {1})
```

Tests: `frontend/api/__tests__/aggregator-proxy.test.js` runs the full matrix per provider — wrong method 405, bad path 404, encoded traversal 404, bad origin 403 (production), happy path 200, OPTIONS preflight, body cap 413, query smuggle, upstream over-cap 502, upstream error collapse 502. **53 NEW tests; full api/ suite green (13 files, 169 tests).**

### 4.6 FE-HIGH-04 — DCA hardcoded 5% slippage

**Surface:** [`frontend/src/hooks/useDCA.ts`](../frontend/src/hooks/useDCA.ts), [`frontend/src/components/swap/DCATab.tsx`](../frontend/src/components/swap/DCATab.tsx)

### 4.7 FE-HIGH-05 — Limit-order minOut from target, not on-chain

**Surface:** [`frontend/src/hooks/useLimitOrders.ts:284`](../frontend/src/hooks/useLimitOrders.ts#L284)
**Closed:** commit `4b3a47f`

At execute-time the hook now re-quotes the AMM via `getAmountsOut` and computes `minOut = min(targetDerivedMinOut, onChainOut * (1 - slippage))`. Stale-target gate aborts cleanly if `targetDerivedMinOut > 2 * onChainOut` so unsatisfiable orders don't burn gas on guaranteed reverts. ### 4.8 FE-HIGH-06 — Custom-token decimals/symbol spoofing + unlimited approval

**Surface:** [`frontend/src/hooks/useSwap.ts`](../frontend/src/hooks/useSwap.ts), [`frontend/src/hooks/useSwapAllowance.ts`](../frontend/src/hooks/useSwapAllowance.ts), [`frontend/src/pages/TradePage.tsx`](../frontend/src/pages/TradePage.tsx)
**Closed:** commit `4b3a47f`

Three coupled hardenings:

- **`useSwap`:** on first hydration, every persisted custom token's on-chain `symbol` + `decimals` is verified via `publicClient.readContract`. Mismatches are evicted with a toast warning. `addCustomToken` does the same re-verify before accepting. `isFromTokenCustom` / `isToTokenCustom` are surfaced for the consumer.
- **`useSwapAllowance`:** refuses `approve(MAX_UINT256)` for any token NOT in `DEFAULT_TOKENS`. Falls back to exact-amount approval and toasts the user. A phisher's localStorage write can no longer trick the user into approving an attacker contract for unlimited transfers.
- **`TradePage`:** permanent unverified-token banner above the swap form whenever from/to is custom.
