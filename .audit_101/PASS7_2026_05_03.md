**Auditor:** Claude Code multi-agent — three parallel general-purpose subagents (oracle/AMM/fees, staking/governance, lending/NFT) on isolated worktrees, plus a manual main-session consolidation pass after the meta-agent watchdog'd on a long forge build.

**Scope:** ~25.7k LOC across all 31 in-tree contracts under `contracts/src/`, attacking the ground claimed closed by 6 prior internal passes (`AUDITS.md`, `FIX_STATUS.md`, `.audit_101/PASS6_2026_05_03.md`) plus the Spartan external review (Apr 16). ## 0. Executive Summary

Pass-7 surfaced **13 NEW findings** (1 Critical / 6 High / 4 Medium / 1 Low / 1 Info) across three independently-attacked bucket scopes, each backed by a runnable Foundry PoC. The Critical (`PASS7-HOOK-01`) is a structural V4 hook accounting bug — `TegridyFeeHook.afterSwap` returns a positive `feeAmount` but never calls `poolManager.take()` inside the unlock context, so **every swap routed through the hook reverts with `CurrencyNotSettled`** the moment it lands on a real V4 PoolManager. The hook is undeployed today (latent), but `script/DeployTegridyFeeHook.s.sol` is fully prepared and the bug would brick every V4 pool integration on day one. The 6 Highs cluster around two themes: (a) the cross-contract per-tokenId reward-bucket architecture is fragile in ways that 6 passes did not exhaust (LD-PASS7-H1/H2/H3, NFTLD-PASS7-H1) and (b) Pass-6 closures were applied asymmetrically — protections present on one surface are missing on its sibling (PASS7-TWAP-01 fail-open carve-out, PASS7-GAUGE-H1 re-add direction, NFTLD-PASS7-M1 carve-out missing on NFTLending). 22 attacks were attempted and held.

## 3. Per-Finding Write-Ups

### 3.1 PASS7-HOOK-01 — V4 hook delta never settled (CRITICAL)

**Surface:** [`contracts/src/TegridyFeeHook.sol:200-285`](contracts/src/TegridyFeeHook.sol#L200) — `afterSwap`

**Originally tracked as:** Bucket A `PASS7-HOOK-01`

**Attack path:**
1. Owner deploys TegridyFeeHook via `script/DeployTegridyFeeHook.s.sol` (CREATE2 salt-mined for flag bitmask 0x0044). Wires it to a TOWELI/WETH V4 pool via `PoolManager.initialize(key, sqrtPrice)`.
2. Any swap on that pool triggers V4 PoolManager → `TegridyFeeHook.afterSwap(...)` (L200).
3. Inside `afterSwap`, the hook computes `feeUint = absAmount * feeBps / 10000`, writes `accruedFees[creditToken] += feeUint`, and returns `(IHooks.afterSwap.selector, int128(uint128(feeUint)))`. **No `manager.take(...)` call inside the unlock context.**
4. The PoolManager's `Hooks.afterSwap` library reconstructs the `hookDelta` and adds it to the hook's account via `_accountPoolBalanceDelta`. `_accountDelta` increments `NonzeroDeltaCount` because the hook's delta went from 0 to positive.
5. The swap router's `unlockCallback` settles the CALLER's swap delta only — the HOOK's positive delta stays.
6. PoolManager's `unlock()` close: `if (NonzeroDeltaCount.read() != 0) CurrencyNotSettled.selector.revertWith();` → **the entire swap reverts**.

**Preconditions:** Block: any block after V4 hook deploy + pool init. Balances: any non-zero swap amount on a pool with `feeBps > 0`, hook NOT paused. Role: any user with token balance. Market: irrelevant — bug is structural.

**Quantified impact:** 100% of swaps on every V4 pool with TegridyFeeHook attached revert. 0% of V4 fee revenue captured. Any LP migrating to a hook-gated V4 pool finds the pool unswappable. Aggregator integrations (UniversalRouter, 1inch, ParaSwap) burn gas and show "swap failed" — kills volume permanently. Reputational damage cascades.

**Suggested fix:** Inside `afterSwap`, before returning, call `poolManager.take(feeCurrency, address(this), feeUint)` to settle the hookDelta within the unlock context. Then refactor `claimFees` to forward the hook contract's IERC20 balance to `revenueDistributor` via `safeTransfer` — no PoolManager interaction needed. **This single change auto-resolves PASS7-HOOK-03**. Reference: `lib/v4-core/src/test/FeeTakingHook.sol:48`.

**PoC:** [`contracts/test/PASS7_HOOK_01.t.sol`](contracts/test/PASS7_HOOK_01.t.sol) — `test_PASS7_HOOK_01_swapRevertsCurrencyNotSettled` (PASS, `vm.expectRevert(CurrencyNotSettled.selector)` fires). Sister tests `_swapClosesCleanlyWhenPaused` (control) and `_claimFeesRevertsManagerLocked` (compounding bug). Run: `cd contracts && forge test --match-path test/PASS7_HOOK_01.t.sol -vvv`. Note: PoC uses faithful mock of PoolManager because the foundry remappings (`solmate/=lib/solmate/src/`) are incompatible with v4-core's `solmate/src/...` import path; bug is structural and would manifest identically on real V4 mainnet.

### 3.2 PASS7-TWAP-01 — First-obs bypass leaks via `!found` fallback (HIGH)

**Surface:** [`contracts/src/TegridyTWAP.sol:705-738`](contracts/src/TegridyTWAP.sol#L705) — `_getCumulativePricesOverPeriod`

**Originally tracked as:** Bucket A `PASS7-TWAP-01`

**Attack path:**
1. Attacker creates a TegridyPair (or uses a freshly-deployed one) with deeply skewed reserves R1 = (100 TOWELI, 0.01 ETH) — spot price 0.0001 ETH per TOWELI vs ~1 ETH realistic.
2. Attacker calls `twap.update(pair)`. `count == 0` branch (L309-331) bootstraps slot 0 with `bypassed = true`, captures manipulated `lastSpot`, sets `lastBypassUsed[pair] = block.timestamp`.
3. Wait `MIN_PERIOD` (15 min). Small organic-looking swap drifts reserves to R2 = (95 TOWELI, 0.0105 ETH) — within the 50% deviation gate.
4. `twap.update(pair)` again. `count == 1` branch runs deviation gate vs the also-manipulated `lastSpot` from step 2 — passes trivially. Slot 1 recorded with `bypassed = false`. Now `count == 2`.
5. **Trigger:** consumer calls `twap.consult(pair, toweli, X, period)` with `period > 16 min`. POLAccumulator's `TWAP_PERIOD = 30 minutes` qualifies.
6. Inside `_getCumulativePricesOverPeriod`: `targetTimestamp = T+16min - 30min = T-14min`. The wrap-aware "before" comparison vs obs[0] returns false; loop ends with `found = false`. Fallback at L705-714 anchors `best = obs[0]` (the bypassed bootstrap).
7. Bypass guard at L738 is `if (best.bypassed && found) revert OracleRebootstrapping();` — `found=false` → SKIPPED. Returns price derived from manipulated bootstrap.

**Preconditions:** Block: after first or second `update()` on a brand-new (or `executeAdminResetPair`-reset) pair. Balances: attacker controls the manipulated initial liquidity (could be < $1 if pair untouched, or flash-loan-funded). Role: any caller can `update()`; consumer just needs `period > MIN_PERIOD`. Market: attacker must be first or one of first two TWAP observers — easy on freshly-deployed pairs via mempool monitoring.

**Quantified impact:** POL `_twapMinOut` floor set against manipulated baseline → up to 99.5% MEV bleed per accumulate call (`TWAP_SAFETY_BPS = 50 bps` × accumulated ETH per call, capped at `MAX_ACCUMULATE_CAP = 100 ETH`). For executeHarvestLP, up to 10% of `totalLPCreated` per call (`MAX_HARVEST_BPS`). TegridyLending's `lastBypassUsed` cooldown (60 min) shields lending in the bootstrap window but does NOT defend against the (count = 2-3, period > gap) sweet spot after the cooldown expires. Aggregate: ~0.5% of POL annual flow at risk during attack window.

**Suggested fix:** Drop the `&& found` condition at L738 — change `if (best.bypassed && found)` to `if (best.bypassed)`. Consequence: consumers reading sparse pairs where the only available anchor is the bypassed bootstrap revert instead of returning a poisoned price (fail-closed, exactly what FRESH-EYES H-3 was meant to ensure). The "graceful degradation" rationale in NatSpec L729-737 is wrong — degrading to a manipulated price IS the bug. If consumers want fail-open behavior on sparse pairs, they should consult `lastBypassUsed[pair]` explicitly (as TegridyLending does).

**PoC:** [`contracts/test/PASS7_TWAP_01.t.sol`](contracts/test/PASS7_TWAP_01.t.sol) — `test_PASS7_TWAP_01_consultReturnsPoisonedPriceFromBypassedBootstrap` (PASS — consult returns `99999999999999 wei = ~0.0001 ETH per TOWELI`, matching the manipulated baseline). Sister tests `_threeObsConsultUnaffected` (control) and `_polAccumulatorPeriodWindowOpensBypass` (DOC proof). Run: `cd contracts && forge test --match-path test/PASS7_TWAP_01.t.sol -vvv`.

### 3.3 PASS7-GAUGE-H1 — Permanent brick of gauge-removal surface (HIGH)

**Surface:** [`contracts/src/GaugeController.sol:842-878`](contracts/src/GaugeController.sol#L842) — `executeRemoveGaugeNextEpoch`, `executeRemoveGaugeFinalize`, `proposeAddGauge`, `cancelRemoveGauge`. Combined with TimelockAdmin `_cancel` revert behavior at L156.

**Originally tracked as:** Bucket B `PASS7-GAUGE-H1`

**Attack path:**
1. Pre: gauge G whitelisted (`isGauge[G] = true`, in `gaugeList`). Owner key (or compromised multisig) is the actor.
2. **T+0:** owner calls `proposeRemoveGauge(G)`. `pendingGaugeRemove = G`. TimelockAdmin `_executeAfter[GAUGE_REMOVE] = T + 24h`.
3. **T+24h:** owner calls `executeRemoveGaugeNextEpoch()`. `_execute(GAUGE_REMOVE)` clears `_executeAfter[GAUGE_REMOVE] = 0`. `isGauge[G] = false`. `pendingGaugeRemove` STAYS `= G`. `gaugeList` unchanged.
4. **T+24h:** owner calls `proposeAddGauge(G)`. Only checks `if (isGauge[G]) revert GaugeAlreadyExists()` — `false`, so passes. `pendingGaugeAdd = G`. New TimelockAdmin proposal `GAUGE_ADD`.
5. **T+48h:** owner calls `executeAddGauge()`. `isGauge[G] = true`; `gaugeList.push(G)` → G now in gaugeList **TWICE**.
6. **Permanent state corruption:** `pendingGaugeRemove == G`, `isGauge[G] == true`, `_executeAfter[GAUGE_REMOVE] == 0`.

**Why no recovery exists:**
- `executeRemoveGaugeFinalize()`: reads `gauge = pendingGaugeRemove` (G), then `if (isGauge[gauge]) revert GaugeAlreadyExists()` → REVERTS.
- `cancelRemoveGauge()`: calls `_cancel(GAUGE_REMOVE)`, which checks `if (_executeAfter[key] == 0) revert NoPendingProposal(key)` → REVERTS.
- `proposeRemoveGauge(*)`: blocked by `if (pendingGaugeRemove != address(0)) revert GaugeRemovePending()`. **ALL future gauge removals permanently DOS'd.**

**Preconditions:** owner key cooperation. Cost: only timelock waits (48h total). No TOWELI burn, no economic significance.

**Quantified impact:** Permanent — gauge-removal surface bricked for the lifetime of the contract. `gaugeList` contains a duplicate; off-chain UIs render G twice. With each future remove-then-re-add cycle (which the brick does NOT prevent — only REMOVE is bricked), more duplicates accumulate. At `MAX_TOTAL_GAUGES = 50`, eventually **legitimate `proposeAddGauge` for new gauges is also DOS'd** (L754). Owner-only attack today (single-key griefing); with multisig migration requires N-of-M cooperation. Recovery requires GaugeController redeploy + state migration — equivalent to a partial protocol restart.

**Suggested fix:** Combination of two changes:
1. Block re-add while pendingGaugeRemove == gauge — add to `proposeAddGauge`: `if (pendingGaugeRemove == gauge) revert GaugeRemovePending();`
2. Make `cancelRemoveGauge` always-clear (defensive): clear `pendingGaugeRemove = address(0)` regardless of timelock state, without reverting on already-executed proposals.

**PoC:** [`contracts/test/PASS7_GAUGE_01.t.sol`](contracts/test/PASS7_GAUGE_01.t.sol) — `test_pass7_gauge_duplicateOnReAdd` (full attack flow, asserts duplicate + bricked surfaces) and `test_pass7_gauge_singleBrick` (minimal repro). Both PASS. Run: `cd contracts && forge test --mt test_pass7_gauge -vv`.

### 3.4 PASS7-LENDING-01 — TegridyLending.acceptOffer missing LD-NEW-H2 sibling (HIGH)

**Surface:** [`contracts/src/TegridyLending.sol:769`](contracts/src/TegridyLending.sol#L769) — `acceptOffer` inbound `staking.transferFrom`

**Originally tracked as:** Bucket C `LD-PASS7-H1`

**Cluster:** Part of PASS7-LENDING-01/02/03 + PASS7-NFTLENDING-01 (architectural cluster).

**Attack path:**
1. Governance whitelists a new staking-shaped collateral via 48h timelock. The contract is later discovered malicious — OR future migration deploys an upgradeable staking proxy that becomes hostile post-deploy. Pass-6 LD-NEW-H2 already treats this trust profile as in-scope.
2. Lender posts an offer naming this collateral; principal escrowed at lending.
3. Borrower has a position NFT on the malicious staking contract.
4. `lending.acceptOffer(offerId, tokenId)` runs: validates offer/lock/whitelist, flips `offer.active = false`, pushes loan record, then `staking.transferFrom(msg.sender, address(this), _tokenId)` — malicious contract returns successfully WITHOUT moving the token.
5. `activeLoansAgainstCollateral` increments. Origination fee + principal flow to borrower.
6. **Lender loses entire principal; borrower keeps both NFT and principal.**

**Preconditions:** A whitelisted collateral whose `transferFrom` can silently no-op (governance-controlled whitelist; pass-6 explicitly treats as in-scope). Active offer exists. Borrower owns the malicious tokenId at acceptance.

**Quantified impact:** Lender loses entire posted principal (up to `MAX_PRINCIPAL_CEILING = 100,000 ETH` per offer). Borrower walks with both NFT and principal. `activeLoansAgainstCollateral` increment falsely blocks subsequent legitimate `executeAcceptedCollateral(remove)` calls until `claimDefaultedCollateral` succeeds — but that path is also broken via PASS7-LENDING-02.

**Suggested fix:** Mirror LD-NEW-H2 exactly:
```solidity
staking.transferFrom(msg.sender, address(this), _tokenId);
if (staking.ownerOf(_tokenId) != address(this)) revert CollateralNotEscrowed();
```
Add `error CollateralNotEscrowed();` to TegridyLending. NFTLending already uses this pattern at L506-508.

### 3.6 PASS7-LENDING-03 — Settled-vs-settled cross-loan drain via shared per-tokenId bucket (HIGH)

**Surface:** [`contracts/src/TegridyLending.sol:894-908`](contracts/src/TegridyLending.sol#L894) (`repayLoan` two-phase pull), [`L1000-1014`](contracts/src/TegridyLending.sol#L1000) (`claimDefaultedCollateral` two-phase pull). Cross-contract: [`contracts/src/TegridyStaking.sol:1484-1527`](contracts/src/TegridyStaking.sol#L1484) (`claimUnsettledForTokenId`).

**Originally tracked as:** Bucket C `LD-PASS7-H3`. **Most architecturally significant finding of pass-7.**

**Cluster:** Part of PASS7-LENDING-01/02/03 + PASS7-NFTLENDING-01 (architectural cluster). The per-tokenId reward bucket having no per-loan attribution is the root cause.

**Attack path:**
1. Alice opens `loanA` on tokenId X. Lock has headroom.
2. Loan accrues `rewardPerTokenStored` over several days.
3. **Staking is paused** (admin emergency, accidental, or hardening response).
4. Alice repays `loanA`:
   - `try staking.claimUnsettledForTokenId(tokenId, alice)` REVERTS (paused, `whenNotPaused`). Try/catch absorbs; emits `EscrowRewardsClaimDeferred`.
   - `staking.transferFrom(address(this), alice, tokenId)` succeeds (OZ ERC721 has NO `whenNotPaused`). Triggers `_settleRewardsOnTransfer(tokenId, lending)` which credits `unsettledRewardsByTokenId[X] += K1` AND `unsettledRewards[lending] += K1` (lending is `_isTrackedHolder`).
   - Second `try staking.claimUnsettledForTokenId(tokenId, alice)` REVERTS (still paused). Try/catch absorbs.
5. Alice receives the NFT. K1 stays parked in `unsettledRewardsByTokenId[X]` and `unsettledRewards[lending]` — settlement deferred.
6. Staking unpauses. Alice does NOT immediately call `pullEscrowRewards(loanA)` (recovery window open but unused).
7. Alice transfers tokenId X to Bob (after 24h staking transfer cooldown). Bob opens `loanB` on the same tokenId.
8. Bob repays. The repay path's `try claimUnsettledForTokenId(tokenId, bob)` SUCCEEDS now — it sees `unsettledRewardsByTokenId[X] = K1 + new` and `holderUnsettled = unsettledRewards[lending] = K1 + new`. `paid = min(perTokenIdTotal, holderUnsettled, rewardPool)` drains EVERYTHING to Bob.
9. Per-tokenId bucket for X is now ≈ 0.
10. Alice eventually calls `pullEscrowRewards(loanA)`. The LD-NEW-H1 gate sees `ownerOf(X) != lending` (NFT at Bob), so per-tokenId pull is allowed. But bucket is empty. `paid = 0`. **Alice's K1 is gone.**

**Why LD-NEW-H1 doesn't defend:** the LD-NEW-H1 gate at [TegridyLending.sol:1620-1633](contracts/src/TegridyLending.sol#L1620) checks `ownerOf == address(this)` to refuse `pullEscrowRewards` on an active loan. But Bob's settlement uses the INTERNAL two-phase pull in `repayLoan` (not via `pullEscrowRewards`), and that internal path has NO per-loan attribution check. The shared `unsettledRewardsByTokenId[tokenId]` is drained as a whole.

**Preconditions:** Staking is paused at the moment Alice's loan settles (any of: emergency, scheduled maintenance, multi-pause cycle). Same tokenId is reused for a subsequent loan. Note: the `pullEscrowRewards` "second-chance" path was specifically designed for the deferred case but is now compromised by the new loan's settlement.

**Quantified impact:** Per-loan settlement-period rewards lost. With current `MAX_LOCK_DURATION = 4 years`, `MAX_PRINCIPAL_CEILING = 100k ETH`, deferred slice can be 1–5% of loan's principal-equivalent in TOWELI rewards. Mainnet relevance: TOWELI rewards are non-trivial (1e18 reward rate at construction); a single full-lock multi-day position could accumulate hundreds-thousands of TOWELI in deferred credit, drainable by any subsequent loan's borrower or lender.

**Suggested fix (two viable patterns, either alone sufficient):**
- **(a) Snapshot-and-delta at loan acceptance.** In `acceptOffer`, snapshot `unsettledRewardsByTokenId[tokenId]` at the moment the loan opens. The two-phase pull at settlement only drains the DELTA (`current - snapshot`). Carry the pre-loan slice in an `escrowRewardsOwed[priorLoanId]` ledger that `pullEscrowRewards` can reach. **Smaller patch.**
- **(b) Per-loan attribution mapping in TegridyStaking.** Extend `claimUnsettledForTokenId` to take a `loanScopeKey` (e.g., `keccak256(abi.encode(lending, loanId))`); track per-`(holder, scope)` credits. Lending pulls only its own scope. **More invasive but architecturally cleaner.**

**PoC:** [`contracts/test/PASS7_LENDING_03.t.sol`](contracts/test/PASS7_LENDING_03.t.sol) — `test_PASS7_LENDING_03_settledVsSettledCrossLoanDrain`. PASS. Run: `cd contracts && forge test --mt test_PASS7_LENDING_03 -vvv`.

### 3.7 PASS7-NFTLENDING-01 — `claimStuckCollateral` silently deletes recovery right (HIGH)

**Surface:** [`contracts/src/TegridyNFTLending.sol:721-741`](contracts/src/TegridyNFTLending.sol#L721) — `claimStuckCollateral`

**Originally tracked as:** Bucket C `NFTLD-PASS7-H1`

**Cluster:** Part of PASS7-LENDING-01/02/03 + PASS7-NFTLENDING-01 (architectural cluster).

**Attack path:**
1. Whitelisted ERC-721 collection becomes (or always was) malicious — `transferFrom` is a SILENT NO-OP for all transfers.
2. Loan opens (inbound honest in this scenario; or selectively malicious only outbound).
3. Borrower repays. The Pass-6 LD-NEW-H2 `_safeOutboundTransfer` correctly detects the no-op and seeds `stuckCollateralRecipient[loanId] = borrower`. ✓
4. Borrower waits, hopes the collection becomes honest, calls `claimStuckCollateral(loanId)`.
5. The function: checks recipient != 0, checks `msg.sender == recipient`, then `delete stuckCollateralRecipient[_loanId];` (CEI), then `IERC721(collateralContract).transferFrom(address(this), recipient, tokenId);`.
6. Malicious collection's `transferFrom` returns successfully without moving. Mapping is now zero. Event fires lying about the outcome.
7. Future calls revert `NoStuckCollateral`. **Borrower's recovery channel permanently gone, even if collection later becomes honest.**

**Preconditions:** Malicious whitelisted collection that keeps no-op'ing across multiple settlement attempts (same trust model as LD-NEW-H2). Borrower must call `claimStuckCollateral` while collection is still malicious — entirely realistic since borrower has no on-chain signal of "collection is now honest".

**Quantified impact:** Borrower's NFT permanently locked. Pre-fix (LD-NEW-H2 only) the same loss occurred at the repay leg; post-fix the loss is moved to the recovery leg. The Pass-6 fix does not save the borrower if the collection remains malicious.

**Suggested fix:** Apply the same post-condition check `_safeOutboundTransfer` already does:
```solidity
function claimStuckCollateral(uint256 _loanId) external {
    if (_loanId >= loans.length) revert InvalidLoanId();
    address recipient = stuckCollateralRecipient[_loanId];
    if (recipient == address(0)) revert NoStuckCollateral();
    if (msg.sender != recipient) revert NotStuckCollateralRecipient();
    Loan storage loan = loans[_loanId];
    bool moved = _safeOutboundTransfer(loan.collateralContract, address(this), recipient, loan.tokenId);
    if (!moved) revert StuckCollateralStillStuck();
    delete stuckCollateralRecipient[_loanId];
    emit StuckCollateralClaimed(_loanId, recipient, loan.tokenId);
}
```

### 3.11 PASS7-NFTLENDING-02 — `cancelRemoveCollection` retry counts cancels of EXPIRED proposals (MEDIUM)

**Surface:** [`contracts/src/TegridyNFTLending.sol:996-1011`](contracts/src/TegridyNFTLending.sol#L996)

```solidity
}
```

### $10M TVL — **NOT ACCEPTABLE without these 4 fixes**

At $10M, attacker economic motivation crosses the threshold where the (count = 2-3, period > gap) TWAP sweet spot becomes worth pre-staging, and the cross-loan attribution race becomes worth orchestrating. Required closures:

1. **PASS7-TWAP-01** — drop the `&& found` carve-out; consumer-side TWAP MUST be fail-closed on bypassed anchors.

4. **PASS7-LPFARM-M1** — auto-refresh boost in `updateReward`. Stale-boost over-credit at 29-300% scale is incompatible with $10M LP TVL.

PASS7-LENDING-01/02 + PASS7-NFTLENDING-01 still latent at $10M IF the whitelist remains static. Add them to the must-fix if any new collateral is being whitelisted.

### $100M TVL — **NOT ACCEPTABLE without paid firm engagement post-fixes**

At $100M, the protocol enters territory where the pattern of "shared mutable state across contracts that pass-7 surfaced (LD-PASS7-H3, PASS7-GAUGE-H1, PASS7-LPFARM-M1) needs a focused human auditor sweep. Six prior internal passes + Spartan + Pass-7 still missed PASS7-HOOK-01 (a structural V4 accounting bug). The pattern is: AI sweeps catch arithmetic / access-control / single-function bugs; they miss subtle interactions between two correctly-individually-scoped mitigations and domain-specific protocol semantics (V4 hook accounting, Curve-style commit-reveal interactions, cross-contract escrow attribution). **Required:** complete all 13 Pass-7 closures + commission a paid firm engagement (Spearbit / OpenZeppelin / ChainSecurity caliber) with explicit scope including the architectural cluster (per-tokenId attribution + V4 hook + boost-cache lifetime). Post-firm closure, a final invariant-suite re-run with targets ≥ 5M calls per surface.

### Top 3 residual risks (even if all Pass-7 closures land)

1. **Cross-contract per-tokenId reward bucket architecture is fundamentally fragile.** Future shared-state additions (any new tracked-holder contract joining `_isTrackedHolder`) re-opens variants of LD-PASS7-H3. Consider migrating to per-loan attribution (LD-PASS7-H3 fix pattern (b)) as the long-term architectural answer.
2. **V4 hook accounting is sufficiently subtle that even after PASS7-HOOK-01 is fixed, related issues are likely** around `BeforeSwapDelta` sign conventions, exactInput vs exactOutput handling, hook delta exceeding swap delta, dynamic-fee bounds at extreme prices. Pass-7 surfaced two compounding bugs (HOOK-01 + HOOK-03); a third in this cluster is plausible. Strong recommendation: do not deploy V4 hook to mainnet without an external V4-hook-specialist review (the Bunni-class footguns this exact pattern).
3. **Cached cross-contract derived state can go stale.** PASS7-LPFARM-M1 is one instance of a broader pattern. Other such caches likely exist (RevenueDistributor's `epoch.totalLocked` snapshots, GaugeController weight snapshots, Restaking's cached boostedAmount). They appear safe today but warrant a focused sweep specifically for "the cached value can outlive the underlying state it was derived from."

## 7. Disagreements with Prior Passes

### 7.1 `FIX_STATUS.md` overstates Pass-6 TWAP HIGH-3 closure
[`FIX_STATUS.md:62-65`](FIX_STATUS.md#L62) and [`PASS6_2026_05_03.md:127-135`](.audit_101/PASS6_2026_05_03.md#L127) claim first-observation manipulation is fully closed. ### 7.2 `Pass6_TWAPFirstObsBypass.t.sol` invariant is weaker than its documented intent
The invariant asserts post-conditions on the LATEST observation but not on the lookup-window anchor when `found=false`. The 13 props × 1.664M calls passed because the property doesn't catch the hole. Tighten: snapshot `best.bypassed` directly in `doConsultProbe`; assert no consult that returns > 0 may anchor on a bypassed observation.

### 7.3 Pass-6 N-1 fix description (`PASS6_2026_05_03.md` §3.2 "GaugeController orphan") is incomplete
Claims "forcing the operator to call `cancelRemoveGauge` or wait for the in-flight remove to land before staging the next." The "or wait" pathway is FALSE — `cancelRemoveGauge` reverts `NoPendingProposal` once `executeRemoveGaugeNextEpoch` has consumed the timelock proposal. There is NO pathway to clear `pendingGaugeRemove` once a re-add lands. Pass-6 closed the orphan-add direction but did not foresee the symmetric re-add ordering. **PASS7-GAUGE-H1 demonstrates.**

### 7.4 Pass-6 LD-NEW-H1 closure description is incomplete
[`FIX_STATUS.md:44-47`](FIX_STATUS.md#L44) describes the gate correctly for the ACTIVE-vs-SETTLED axis. It does NOT close the SETTLED-vs-SETTLED axis (LD-PASS7-H3). Narrow the description: "Closes the active-vs-settled cross-loan drain via `pullEscrowRewards`. Does NOT close the settled-vs-settled drain via the internal two-phase pull invoked from `repayLoan` / `claimDefaultedCollateral` — see PASS7-LENDING-03."

### 7.5 Pass-6 LD-NEW-H2 closure description is incomplete
[`FIX_STATUS.md:56-58`](FIX_STATUS.md#L56) correctly describes the repayLoan / claimDefault legs. It does NOT mention that:

### 7.6 Pass-6 FRESH-EYES L closure is incomplete
[`FIX_STATUS.md:173-188`](FIX_STATUS.md#L173) polish batch describes the still-live carve-out applied to TegridyLending. It does NOT mention that the same code shape exists on TegridyNFTLending.cancelRemoveCollection and was NOT updated. **See PASS7-NFTLENDING-02.**

### 7.7 `010_TegridyLPFarming.md` H-1 incorrectly downgraded
H-1 caveat "verify TegridyStaking's lock semantics" ended up insufficient. The flash-loan path IS mitigated by TRANSFER_COOLDOWN, but the LEGITIMATE-then-stale path (PASS7-LPFARM-M1) is not. The 4.5x ceiling clamp doesn't help — issue is cache lifetime, not ratio cap. Promote H-1 from "low-risk because flash-loan is gated" to "MEDIUM, requires `updateReward` auto-refresh."

### 7.8 Pass-6 INV-G5 (DropV2 payment conservation) handler scope
[`Pass6_DropV2SupplyConservation.t.sol`](contracts/test/invariants/Pass6_DropV2SupplyConservation.t.sol) asserts `sum(paidPerWallet) <= totalProceeds`. The handler does NOT expose `withdraw()` — and `withdraw()` resets `totalProceeds = 0` while leaving `paidPerWallet[*]` non-zero. The invariant would FAIL post-withdraw. **Doc-level overstatement, not a vulnerability.** Recommend either (a) expand handler to call `withdraw` + weaken invariant to `paidPerWallet ≤ totalProceeds + sum(withdrawnAmount)`, or (b) explicitly document that scope excludes post-withdraw state.

### 7.9 Architectural inconsistency between TegridyLending and TegridyNFTLending pause invariant
TegridyNFTLending.effectiveDeadline (LD3-M4 / LD2-L2) reverts `PauseInvariantViolated` if `loan.pausedDurationAtStart > totalPausedDuration`. TegridyLending.effectiveDeadline silently clamps to 0 instead. Both should apply the same fail-loud pattern documented as the LD2-L2 fix. Not exploitable today, but architectural debt.

### 7.10 Pass-6 SLITHER triage framing
[`PASS6_SLITHER_2026_05_03.md`](.audit_101/PASS6_SLITHER_2026_05_03.md) "headline result: zero NEW actionable findings" is correct relative to slither's detector set.
