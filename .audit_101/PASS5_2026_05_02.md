## 2. PASS5-REV-H1 — the only HIGH

### 2.1 Statement

Two permissionless entrypoints distribute new ETH to stakers:

```solidity
// RevenueDistributor.sol:296-298
function distribute() external nonReentrant whenNotPaused {
    _distribute();
}

// RevenueDistributor.sol:309-320
function distributePermissionless() external nonReentrant whenNotPaused {
    // AUDIT FIX M-12: Prevent distribution at low stake levels to avoid concentration attacks
    require(votingEscrow.totalBoostedStake() >= MIN_DISTRIBUTE_STAKE, "STAKE_TOO_LOW");
    ...
    _distribute();
    emit PermissionlessDistribution(msg.sender, epochs.length - 1);
}
```

The M-12 fix on `distributePermissionless` blocks the canonical concentration attack — but the sibling `distribute()` lacks the same `MIN_DISTRIBUTE_STAKE` check and is *also* permissionless (no `onlyOwner`, no role gate). Calling `distribute()` directly bypasses M-12 entirely.

### 2.2 Attack chain (cross-contract: TegridyStaking ↔ RevenueDistributor)

1. Attacker holds a small staking position (any non-zero `boostedAmount`).
2. Attacker monitors a whale lock-expiry event (or a pending unstake / `requestEmergencyExit`).
3. As soon as the whale's lock is past `lockEnd`, attacker calls **TegridyStaking.kick(whale_tokenId)** (`kick` is permissionless: `external nonReentrant whenNotPaused`, [TegridyStaking.sol:954](../contracts/src/TegridyStaking.sol#L954)). The kick zeroes the whale's `boostedAmount` and writes a `_totalBoostedStakeCheckpoint` reflecting the post-kick total.
4. In the next block, attacker calls **`RevenueDistributor.distribute()`** (the unprotected sibling).
5. `_distribute()` reads `totalBoostedStakeAtTimestamp(block.timestamp - 1)` — this is the post-kick checkpoint. Epoch is created with a tiny `totalLocked`, the attacker's small stake is now ~100% of the snapshot.
6. Attacker calls `claim()` → captures up to ~100% of the queued epoch ETH (capped per-epoch by C-03 fix at `epoch.totalETH`).

### 2.3 Reproduced PoC

`forge test --match-contract PASS5_REV_H1 -vv` produces:

```
Attacker stake (TOWELI): 1.000000000000000000
Epoch ETH:               50.000000000000000000
Attacker gain (ETH):     50.000000000000000000
Honest stakers' loss:    0.000000000000000000
```

Three test cases — including the positive control proving that `distributePermissionless` correctly blocks the same attack. See [`PASS5_REV_H1_DistributeBypass.t.sol`](../contracts/test/pass5_pocs/PASS5_REV_H1_DistributeBypass.t.sol).

### 2.4 Economic impact

- **Gain to attacker:** up to 100% of accumulated `accumulatedETHFees` queued in `RevenueDistributor` since the previous distribute. Realistic single-hit: 5-50 ETH at typical mainnet protocol velocity.
- **Cost to attacker:** opportunity cost of any stake sufficient to be the post-kick epoch's effective denominator (1 wei works; we use 1 ether for realism). At MIN_LOCK = 7 days, the cost is ~7 days of held TOWELI. With $5 TOWELI and 1k staked: ~$35 of opportunity cost per attempt.
- **Repeatability:** every 4 hours (`MIN_DISTRIBUTE_INTERVAL`) per fresh whale exit. Whale lock expiries are visible in advance via on-chain `lockEnd` reads.

### 2.5 Recommended fix

**One-line:** add the same `MIN_DISTRIBUTE_STAKE` guard to `distribute()`:

```solidity
function distribute() external nonReentrant whenNotPaused {
    require(votingEscrow.totalBoostedStake() >= MIN_DISTRIBUTE_STAKE, "STAKE_TOO_LOW");
    _distribute();
}
```

**Stronger:** raise `MIN_DISTRIBUTE_STAKE` from 1000 ether to a value that meaningfully bounds the attack (e.g., 100,000 ether or a `5%-of-totalSupply` floor). The current 1000 ether floor only blocks the trivial "attacker is the only staker" case; the partial-concentration variant remains exploitable. PoC test `test_distribute_concentration_attack_partialConcentration` shows 33% capture from a 5-ether attacker stake against 10-ether honest stake — both well above MIN_DISTRIBUTE_STAKE — succeeding at 16.66 ETH gain.

**Best:** replace MIN_DISTRIBUTE_STAKE with a *time-weighted* check (e.g., require `totalBoostedStakeAtTimestamp(block.timestamp - 1 days) ≥ totalBoostedStakeAtTimestamp(block.timestamp - 1) * 0.9`) — i.e., reject distribute when totalLock has dropped >10% in the past 24h. Mirrors Curve's `gauge_relative_weight_write` time-averaging.

## 3. PASS5-PA-L1 — PremiumAccess revenue drift on extension

### 3.1 Statement

In `PremiumAccess.subscribe`, the extension branch adds `consumedEscrow` to `totalRevenue` ([line 317](../contracts/src/PremiumAccess.sol#L317)) and *then* the always-running tail also adds `cost` ([line 345](../contracts/src/PremiumAccess.sol#L345)). But the initial subscribe already added `cost1` to `totalRevenue` on day-0; `consumedEscrow` (= `cost1 - remainingEscrow`) is therefore counted **twice**.

Math trace:
- Day 0: subscribe(cost1). `totalRevenue += cost1`. `userEscrow = cost1`.
- Day X (extend with cost2):
    - `consumedEscrow = cost1 * X / oldDuration`
    - `totalRevenue += consumedEscrow` (line 317) — but `cost1` was already entirely in `totalRevenue`!
    - `totalRevenue += cost2` (line 345)
- Day X cancel right after extend: `fullRefundable = cost2 + remainingEscrow`. `totalRevenue -= fullRefundable`.
- **Net `totalRevenue` post-cancel:** `cost1 + consumedEscrow + cost2 - cost2 - remainingEscrow = cost1 + consumedEscrow - remainingEscrow = 2 × consumedEscrow`. True earned revenue is `consumedEscrow`. Drift: 1× per consumed slice.

### 3.2 Why LOW (not HIGH)

`totalRevenue` is **only** used as a refund-decrement cap at [line 427](../contracts/src/PremiumAccess.sol#L427) (`if (fullRefundable <= totalRevenue)`). The drift is upward (inflation), so the cap remains satisfied — no underflow, no fund loss. The V3-DR3-M-02 fix is correct on the cancel/shortfall axis. The drift is purely an off-chain metric concern (treasury-revenue dashboards over-report).

### 3.3 Recommended fix

Drop the `totalRevenue += consumedEscrow;` line at 317. Either:
- The initial-subscribe `totalRevenue += cost1` already counted the entire cost as gross-revenue (high-water-mark semantic). Don't re-add.
- OR: split the semantic — make `totalRevenue` track *true earned revenue* with `+= consumedEscrow` only, and remove the always-running `+= cost` at line 345. Either is internally consistent; the current code mixes both semantics.

## 5. Negative findings — categories where pass-5 confirms NO issues

Per the brief, "absence of findings IS a useful audit signal". The following categories were thoroughly explored and yielded **no PoC-backed findings**:

### 5.1 Cross-contract attack chains beyond REV-H1
- Stake → Restake → Vote → Bribe-claim chain: voting power double-counting prevented by NFT custody — see [the cross-contract map](PASS5_2026_05_02/01_stake_vote_bribe_chain.md). No real attack found beyond REV-H1.
- Lend → Borrow → Liquidate chain: TegridyLending claimDefault has both `nonReentrant` and `SequencerCheck.checkSequencerUp`; no callback into AMM during liquidation that doesn't already revert.
- POL → SwapFeeRouter → Splitter → Distributor: the 50k gas stipend on push paths + deferred `pendingDistribution` queue on failure preserves conservation under all paths exercised by INV-B.

### 5.2 Economic / game-theoretic
- **First-depositor share inflation** in TegridyPair: blocked by `MINIMUM_LIQUIDITY * 1000` initial-mint floor at [TegridyPair.sol:155](../contracts/src/TegridyPair.sol#L155).
- **Donation attacks** on accumulator math: covered by `min(checkpointed, current)` clamps in restaking, and Curve-style natural distribution in gauges.
- **JIT staking around distribute**: snapshotTime = `T-1` in `_distribute()` excludes same-block stakes via `Checkpoints.upperLookup` semantics. (PASS5-REV-H1 is a *related* but distinct kick-then-distribute attack; it is NOT same-block JIT.)
- **Sandwich on POLAccumulator.accumulate**: now `onlyOwner` (line 346) — eliminated.

### 5.3 MEV / ordering
- Atomic borrow→vote→repay loops: blocked by C2 `committedPower` cap + DEEP-GOV-01 `min(historical, current)` clamp at every vote site.
- Front-run propose→execute: every protocol-class write is timelocked at 24-48h; no executable proposal can land in the same block as its propose.
- Dutch auction front-running on TegridyDropV2: phase-gate on `setMintPrice` (DEEP-DROP-02) plus the V3-DROP-V2-01 same-block round-trip closure left no in-flight setter window.

### 5.4 Rounding direction
- `TegridyPair.harvest`: kLast capture before `_mintFee` (V3-AMM-M1 fix) means dust accumulation is bounded to ≤1 wei per harvest event.
- `GaugeController` weight math: invariant D2 confirms sum-of-relative-weights ≤ BPS with worst-case loss ≤ num_gauges wei (~1 wei per gauge per epoch — negligible).
- `POLAccumulator` cumulative-price: no production consumer reads its accumulator (TegridyTWAP exists but isn't wired into lending — known M-32 / pass-1 area, not a pass-5 finding).

### 5.5 L2-specific
- `SequencerCheck.checkSequencerUp` is wired into TegridyTWAP, POLAccumulator (`accumulate` + `executeHarvestLP`), TegridyDropV2 (`tryCheckSequencerUp` for view, `checkSequencerUp` for action), TegridyLending (4 sites), TegridyNFTLending (3 sites), MemeBountyBoard. SwapFeeRouter and TegridyRouter have no sequencer check but rely on Uniswap V2 spot pricing which isn't price-discovery-attackable on its own (the protocol's own TWAP gates `convertTokenFeesToETH` minOut downstream).
- Reorg-resistance on commit-reveal: snapshot snap-back to `T - SNAPSHOT_LOOKBACK = T - 1h` in VoteIncentives.advanceEpoch defends.

### 5.6 Centralization / governance capture
- V3-AMM-H1 `sweepETH` fix is correct: `to == revenueDistributor` is the *only* allowed sink ([TegridyFeeHook.sol:564](../contracts/src/TegridyFeeHook.sol#L564)). owner() removed from allowlist.
- Other `owner()` usages (CommunityGrants, MemeBountyBoard, ReferralSplitter, SwapFeeRouter, TegridyRestaking, TegridyStaking) are role-comparison gates, not value-routing — no capture-then-drain analog.

### 5.7 Upgrade / migration hazards
- No proxy/upgrade pattern in production contracts; storage layout drift is not a class-of-bug here.
- Cross-contract address rotations (`applyRevenueDistributor`, `applyPolAccumulator`, `applyReferralSplitter`) are timelocked and their setter validates `polShareBps == 0` / `referralFeeBps == 0` before allowing zero (DEEP-R-M04 / DEEP-R3-M02). No silent fund-orphaning observed.
